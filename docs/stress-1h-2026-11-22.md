# FSD / mothership stability stress — 2026-11-22

> Historical snapshot. The 443 single-socket limit documented below was
> replaced on 2026-11-28 by 4 TLS slots on PSRAM boards (2 without PSRAM) to
> remove the parallel-handshake `mbedtls_ssl_handshake -0x0050` failures.

Firmware: `esp32s3-waveshare-wifi` v1.4.35 (mothership/api-prd parity + DNS default reset)
Device: ESP32-S3, AP `fsd-esp32` / `9.9.9.9`; upstream STA not configured
Client: macOS on the device AP (`9.9.9.10`)

## Traffic

- `tests/tesla_mixed_stress.py`: FSD positive/negative paths, Tesla cloud
  endpoints, GET/POST/PUT/DELETE/HEAD/OPTIONS, TLS 1.2/1.3, ALPN h2, no SNI,
  malformed TLS/HTTP, 6-way bursts, management pages/APIs, DNS A/AAAA/TXT/ANY.
- 4567 mothership probe: plaintext `POST /feature_configuration` every 5 s,
  verifying status/653 B/md5; DNS A for mothership and api-prd.
- Serial `wifi-diag` every 60 s: heap, minHeap, reset reason, FSD counters.

## 1-hour runs (pre-final hardening)

Three 3600 s runs all completed with:

| Item | Result |
|---|---|
| Hard failures | **0** |
| Reboots / uptime resets | **0** |
| Health checks | 208-209 / 209 |
| Management requests | 419-420 / 420 |
| DNS queries | 330 / 330 (later 343 / 343) |
| FSD replies | 588-657 successful, recovery after every burst |
| 4567 mothership replies | 588-590 / 588-590 (after probe fix) |
| FSD final recovery | **yes** |

The first two runs showed a serial `minHeap` low-water of **2.69 KB** and
**1.27 KB** under combined synthetic 6-way TLS bursts + concurrent 4567 probe.
No allocation failure, reset, or crash was observed, but the margin was thin.

## Findings / fixes

1. **4567 probe timeout was a test bug.** httpd keeps HTTP/1.1 connections
   alive; the probe waited for `Connection: close`. Fixed by honoring
   `Content-Length`. 4567 then passed 100% (588-590/590, later 121/121, 240/240).
2. **A TLS cert-select handshake guard was tried and removed.** It serialized
   handshakes/heap-gated them, but false `MBEDTLS_ERR_SSL_ALLOC_FAILED` rejects
   (error `-0x7F00`) caused real FSD failures (`FSD did not recover after
   burst`). The guard was reverted; the vehicle-facing TLS path must not be
   gated on callback-time heap estimates.
3. **Management heavy-response heap guard (kept).**
   - `/`, `/fsd`, `/dash`, `/perf`, `/perf-share`, `/service`, `/client-config`,
     `/api/log`, `/api/fsd-mock/hits|handshakes|config-history`,
     `/api/wifi-bridge/blocked-download`: reject with `503 low_heap` below 18 KB.
   - `/api/status`: reject below 12 KB.
   - `/api/wifi-bridge/status` and `/api/fsd-mock/payload` stay unguarded for
     monitoring/FSD delivery.
4. **Socket limits (kept).**
   - 443: `max_open_sockets=1`, `backlog_conn=1`.
   - 4567: `max_open_sockets=1`, `backlog_conn=1`.

## Notes

- `fsd_error` in the mixed summary is dominated by intentional negative path
  `/feature_configuration%2F`, which the firmware correctly treats as
  non-FSD/502; it is not a device failure.
- Upstream STA was offline, so non-FSD Tesla paths exercised the fast
  `502 [Errno 101] Network is unreachable` path (historical name:
  `upstream_unavailable`) rather than real upstream TLS. FSD, 4567,
  management and DNS paths were fully exercised.
- Remaining low-water margin under synthetic 6-way concurrency is ~12 KB
  (above the 10 KB hard threshold). The car uses one 443 connection, so this
  synthetic case is stricter than real vehicle traffic.
- The final 1-hour run recorded exactly one `handshake.fail` with
  `mbedtls_ssl_handshake returned -0x7200` (INVALID_MAC), coincident with the
  deliberate malformed-record injection. It is the expected rejection of the
  injected garbage record, not a vehicle-path failure; FSD recovered on the
  next request and stayed green for the rest of the run.
